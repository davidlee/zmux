# ADR-003: The wrapper is the product, and it knows no integration

## Context

zmux first planned a Rust binary, then vendoring and patching zp and pi-zmx. On NixOS a wrapper
can be the package itself, so every caller inherits the convention just by calling `zmx`
(DEC-006). The convention must live in one place, or the callers drift from it.

## Decision

We will ship one shell script as the `zmx` package. It rewrites `attach` and `run`, and passes
every other verb through byte for byte. There is no `zmux` verb.

- `attach` that creates: `project` and `id` ride the same call in `--labels`, and the client is
  exec'd through the launcher.
- `run`: creates the session if absent, labels it with `zmx set` because `run` takes no labels,
  then brackets the task with `state` (ADR-002), exiting with the task's own status.

The wrapper knows no integration by name. Its contract is argv and lines, and its launcher is
data. Each integration lives with the tool it belongs to (DEC-011).

## Consequences

### Positive

- zp, pi-zmx, Emacs and zsh conform with no binding and no fork.
- The change is declarative, visible in the derivation, and reverts in one line.

### Negative

- Only calls through the wrapper conform, and it can't decide everything (CON-002).
- A third rewrite is a change to every caller on the machine, so it needs this record revisited.

### Neutral

- The real binary is addressed by absolute path, so the wrapper can't re-enter itself. It is
  `zmx-unwrapped` (DEC-007).
- The default launcher does name `systemd-run`. `ZMX_LAUNCHER` replaces it, and the wrapper falls
  back to none (CON-003).
- `harness/pi/` lives in this repo, but the wrapper doesn't know about it.

## Verification

`tests/run-tests.sh` asserts argv against stub binaries. `nix flake check` runs that, plus
`wrapper-parity`, `zp-uses-wrapper` and `dev-tools-ship-wrapper`.
