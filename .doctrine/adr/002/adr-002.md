# ADR-002: State is written by the party that knows, and nothing watches

## Context

`state` tells a human which session wants them. Labels carry no author or timestamp (EVD-009), so
the label is only as honest as its writers. An observer writing state is a daemon with an
opinion. A dispatcher is not an observer: it knows when it hands work over and when that work
returns.

The tempting fix for a stale or missing `state` is to infer it. ISS-001 is exactly that
temptation.

## Decision

We will treat `state` as intent, and zmx's `ended` and `exit_code` as fact. A reader shows both
and believes neither alone.

- The wrapper, as dispatcher, brackets `zmx run` with `working`, then `done` or `failed`.
- The harness that is asking a human writes `blocked`, and `working` when it resumes (DEC-009).
- A human arriving may clear `blocked`.
- Nothing watches, polls or infers, and nothing else deletes a label.

## Consequences

### Positive

- Each writer writes only what it knows.
- A stale state costs nothing: it is an advertisement, not a lock.

### Negative

- `state` can be stale: `blocked` outlives pi, and a detached dispatch stays `working` (ISS-001).
- A harness with no plugin never reports `blocked`.
- An idle session can read `done` (DEC-006).

### Neutral

- Clearing `blocked` on attach is permitted but not implemented: `do_attach` leaves `state` alone.
- Since 0.1.1 the outcome is written when the task ends, even if the caller was terminated.

## Verification

`tests/run-tests.sh` asserts the wrapper's bracketing, and `tests/zmx-state.test.ts` the pi
plugin's writes. `VOCABULARY.md` § state is the contract, including the reader's ordering.
