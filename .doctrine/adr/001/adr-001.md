# ADR-001: zmux adds a convention to zmx, not a second system

## Context

The inspiration is zmx and tmux. zmx already provides the substrate: sessions, labels, multiple
clients, history. HYP-002 holds that what is missing is legibility, not capability: who is
running, for which project, in what state, and which one wants a human.

Each addition below looks reasonable alone. Together they would rebuild zmx with a worse owner.

## Decision

We will test every proposal twice: does it plug into an affordance zmx already has, and is it
the least code that makes agent work faster?

We will not build:

- **A daemon or server.** zmx has none to hold (CON-001). Survival comes from a scope per session.
- **A reader or TUI of our own.** zp and Emacs read the labels. Splits, tabs and layout belong
  to ghostty and umbriel.
- **A status protocol or screen renderer.** A label does the job (DEC-003), and OSC 7501 doesn't
  survive zmx (EVD-008).
- **A client of zmx's socket.** That is an unstable ABI belonging to someone else (EVD-011).
- **A config tree.**
- **A manifest.** It would be a second source of truth. Sessions are created on demand by name.
  For repeated setup, use a justfile target or a function calling attach N times.
- **A fork of zp or pi-zmx to carry the convention.**
- **`ZMX_SESSION_PREFIX` support.** It is applied after the wrapper computes labels, so label and
  name would disagree (CON-002).

## Consequences

### Positive

- The whole product stays a shell script and a contract.
- There is no state of our own to migrate, repair or keep in step with zmx.

### Negative

- Anything zmx can't do, zmux can't do either.
- A manifest's repeatable setup is given up. Revisit only if a real project needs sessions
  started in an order.

### Neutral

- Deferred, not refused: an MCP server, and agent coordination beyond labels.
- Remote sessions stay open under IDE-001.
- A fork carried for a bug is allowed: pi-zmx's is (DEC-011).
- A need that labels and existing readers can't answer refutes HYP-002 and reopens this record.

## Verification

Design review: nothing mechanical enforces a refusal. A proposal that adds a long-running
process, a store or a socket client needs this record superseded first.
